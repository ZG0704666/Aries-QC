# 展览互动内容制作员 · AI 员工岗位说明书

> 本文件说明这台 AI 员工**负责什么、要什么、交什么、什么时候必须找人、怎么算干完了**。
> 它不是宣传页，是上岗说明书：写进来的每一条都能在代码里指到出处，做不到的明确写「做不到」。

| 项目 | 内容 |
|---|---|
| 岗位名称 | 展览互动内容制作员（Exhibit AI Employee） |
| 岗位编号 | `studio`（服务端口 4182） |
| 服务对象 | 展馆内容负责人、策展人、讲解词编写者 |
| 业务单元 | 一件展品 → 一组展项 → 一套可交付的讲解内容与音频 |
| 上岗条件 | 一个模型 API Key（默认 DeepSeek）+ 本机可用的 TTS 引擎 |
| 交付周期 | 单个展项重做约 1 分钟；五展项整批约 5 分钟（视模型与网络） |

---

## 一、岗位职责

### 1.1 一句话

把「一件展品」变成「观众戴上耳机就能听懂的一段讲解」，并把过程中每一个数字都留成可回查的凭据。

### 1.2 核心任务

| # | 任务 | 员工实际做的事 |
|---|---|---|
| 1 | **依据收集** | 两条路并行：读客户上传的原文；或对公开作品自行联网检索，把网页存成项目内可引用来源（`research_index` / `all_sources`） |
| 2 | **展项规划** | 把一件作品拆成若干展项并定动线顺序；有资料时一份资料一个展项，无资料时先定清单再用项目名兜底（`exhibit_units`） |
| 3 | **内容起草** | 每个展项产出：主讲解（约 45 秒）、简化版（亲子/儿童口吻）、知识卡（≥2 条，每条带可定位引文）、追问与兜底问答（`generate_exhibit`） |
| 4 | **引文核验** | 逐字校验每条引文能否在来源原文里原样出现；找不到就开一条「待核验引用」，不静默放行（`verify`） |
| 5 | **自测** | 跑七项程序化自测，不通过就退回待确认状态，不保留「已自测」的旧结论（`content_tests`） |
| 6 | **音频合成** | 逐展项合成 MP3，并用 ffprobe 现场量真实时长；量不到就算未通过（`measured_duration` / `tts.synthesize`） |
| 7 | **交付打包** | 交付稿 + 音频本体 + 音频说明 + 清单打成一个 zip，字节数与 sha256 全部按磁盘文件重算（`build_export_bundle`） |
| 8 | **闭环记录** | 报价、反馈、候选改进、客户签收都落到项目上并由服务端校验，不接受前端自捏的数字 |

### 1.3 业务范围

**做：**

- 公开/知名作品的讲解内容（自带联网调研能力，不需要客户先提供资料）
- 客户自送藏品的讲解内容（依据只有客户原文，不外扩）
- 单展项独立重做——只重做 EX02，其余展项一字不动（`run_single_exhibit`）
- 中文讲解，可指定语言与观众类型（亲子、成人、专业观众）

**不做：**

- 不替人做审核结论。审核必须有人署名，员工只能提请（见第四节）
- 不承诺设备端能播。耳机/音箱/语音眼镜的真机试播不在员工能力内
- 不编数据。量不到时长就标「未采集」，找不到引文就开待核验，没音频就写「未生成」
- 不保管客户资料出本机。数据库是本地 sqlite 文件，不入仓库

## 二、输入要求

### 2.1 任务发起方

| 角色 | 负责什么 |
|---|---|
| **展馆内容负责人 / 策展人** | 发起任务、提供作品名与观众定位、决定是否采用员工调研到的依据 |
| **资料提供方**（客户或馆方档案） | 只在「资料网上查不到」时出面：自送原文、确认资料授权 |
| **审核人** | 内容定稿前的署名审核，通过或退回 |
| **客户方签收人** | 发布后签署验收结论 |

### 2.2 必要信息

| 项 | 是否必填 | 说明 |
|---|---|---|
| **展品/作品名称** | **必填** | 没有名称项目就建不起来；有名称即可开工，知名作品员工自己去查 |
| **观众类型** | 建议填 | 亲子 / 成人 / 专业观众，决定口吻与难度；不填则按通用口吻起草 |
| **语言** | 建议填 | 默认中文 |
| **简要说明** | 可选 | 客户想强调什么、避免什么，写在里面员工会读 |

**只有一个硬门槛：作品名。** 其余信息缺失时员工会先按合理默认值起草，再在对话里问清楚，不拿「信息不足」当借口停工。

**可选但有用：** 展签文字、馆方口吻样例、禁用词、单段时长要求、报价范围、交付时间。

### 2.3 输入材料：两条路，同权

这是本岗位的关键设计——**上传资料不是开工的硬门槛**。

| 路径 | 适用情形 | 客户要做什么 | 员工做什么 |
|---|---|---|---|
| **A. 客户自送资料** | 自有藏品、未公开资料、网上查不到或查到的很少 | 把原文导进来（展签、藏品档案、既有讲解稿、专家口述整理稿） | 只在这批原文里取材，不外扩、不补写 |
| **B. 自主联网调研** | 公开作品、知名作品（如《蒙娜丽莎》） | 什么都不用给，说一句「先调研一下这个作品，然后起草」 | 自行检索、抓正文、只保留能在正文里**逐字命中**的整句存成摘录（`add_research`）；改写过的句子一律丢 |

两条路的产物都进同一个来源池，之后的内容起草、引文核验、串台检查走同一套逻辑，没有「二等公民」。

### 2.4 材料格式与上限

| 项 | 值 |
|---|---|
| 支持格式 | `txt` `md` `csv` `tsv` `json` `html` `docx`，装了 `pypdf` 后追加 `pdf` |
| 单文件上限 | 20 MB / 40 万字符（`docread.MAX_BYTES` / `MAX_CHARS`） |
| 上传方式 | 界面「＋ 导入资料」或整页拖放；也可在对话里让员工登记一段文字 |
| 段落化 | 服务端按段落切分并编号（`SRC-001·P003`），引文必须能定位到具体段落 |

### 2.5 对材料内容的硬要求

- **必须是原文。** 员工会逐字核对，改写过的句子过不了核验，会变成待核验引用卡住流程。
- **一段话讲一件事。** 混在一起的长段会让引文定位变粗，知识卡质量下降。
- 一件作品资料混乱时，宁可先只导一份最权威的，让员工定好展项清单再补。

## 三、交付成果

### 3.1 成果形态

导出 `/api/studio/projects/<id>/export.zip`，客户拿到的是一个能直接归档的包：

| 文件 | 内容 |
|---|---|
| `交付稿.md` | 首部四行状态：项目状态 / 自测状态 / 审核状态 / 音频状态；逐展项：主讲解、简化版、知识卡（含来源编号与核验标记）、音频指纹行 |
| `音频/EX0n-<引擎>-<内容哈希>.mp3` | 音频本体，真实合成的 MP3。文件名带内容哈希前缀，正文一改必然换名，避免浏览器播到旧音频 |
| `音频/README.md` | 引擎、模型、音色、格式、逐文件字节数与实测时长、sha256 前 16 位，以及**「已验证 / 未验证」两栏明示** |
| `交付清单.json` | 机器可读清单：项目 id、版本、状态、审核记录、自测通过数、每个文件的字节/sha256/时长/引擎/音色 |

状态行不会粉饰：审核没做就写「尚未人工审核——本稿不可当作已验收交付」；音频缺一个就写「不完整——以下展项没有音频：EX03、EX05」。

### 3.2 单展项内容规格

| 内容块 | 规格 | 用途 |
|---|---|---|
| 主讲解 | 80~400 字，实测朗读 33.8~56.3 秒（目标 45 秒 ±25%） | 耳机导览主音频 |
| 简化版 | 更短、更口语，亲子/儿童可用 | 家庭观众、儿童团 |
| 知识卡 | 每展项 ≥2 条，每条含 `text` + `quote` + `source_ref` | 展签二维码、延伸阅读、审核核对 |
| 追问 | 观众可能问的问题与回答 | 语音问答、人工讲解备用 |
| 兜底 | 模型答不上来时的安全回答 | 防止现场冷场或瞎答 |

### 3.3 质量要求（可量化）

| 要求 | 判据 | 谁来判 |
|---|---|---|
| 覆盖完整 | 本轮应有展项与已生成展项集合完全相等，缺/多都算失败 | 程序 |
| 引文可定位 | 每条事实的 `quote` 能在其来源段落中**逐字**找到（标点归一化修复会标记 `repaired`） | 程序 |
| 不串台 | 展项只引用自己登记的来源编号 | 程序 |
| 时长合规 | ffprobe 实测秒数落在窗口内；**有音频却读不出时长 = 未通过**，不拿字数冒充 | 程序 |
| 知识卡充足 | 每个展项至少 2 条事实 | 程序 |
| 主讲解非空 | 每个展项都有正文 | 程序 |
| 无空答 | 追问与兜底每一条都有回答 | 程序 |
| 音色可用 | 人工试听确认语速、断句、口吻符合馆方要求 | **人** |
| 设备可播 | 真机试播 | **人** |

### 3.4 使用场景

- 展厅耳机/导览机：直接播 `音频/` 里的 MP3
- 展签二维码：扫开读 `交付稿.md` 对应展项段落，或接知识卡
- 亲子团/研学：用简化版与兜底问答
- 语音眼镜、导览机器人、数字人：走 `交付清单.json` 的元数据对接

## 四、人工介入

### 4.1 六个必经卡点

| 时机 | 为什么必须人做 | 员工的处理 |
|---|---|---|
| **① 资料授权确认** | 客户自送资料涉及使用权，只有客户能确认 | 未登记授权时界面上标为阻断项；**公开作品走自主调研，不需要这一步** |
| **② 待核验引用处理** | 引文在原文里找不到，可能是模型改写或跨展项串台 | 每条给出三个动作：「补充资料 / 补充资料后再核 / 删除该事实」，逐条处理，不自动放过 |
| **③ 内容改写** | 口径、政治性表述、馆方话术只能人定 | 改完版本 +0.1，**旧自测与旧审核自动失效**，必须重跑重审 |
| **④ 审核署名** | 审核结论会进交付稿与验收凭证，必须有人负责 | 通过和退回都强制填审核人；「通过」要求自测全过且无待核验引用，否则拒绝 |
| **⑤ 发布** | 发布意味着对外交付 | 五道门禁逐条检查，任一条不过就明确报出原因（见 5.3） |
| **⑥ 客户签收** | 验收是客户的权利 | 只有已发布状态才能签收；同一签收人同一结论重复提交视为幂等，换人或改结论直接拒绝 |

### 4.2 员工明确做不到的三件事

1. **试听判断。** 音色好不好、断句对不对、口吻合不合适，只能人听。
2. **真机验证。** 耳机、音箱、语音眼镜能不能播，项目尚未接入真机。
3. **替代审核。** 员工可以自测、可以列出问题，但不能给自己签字。

## 五、验收标准

### 5.1 四道关，顺序不能跳

```
程序自测（7 项全过） → 人工审核（署名通过） → 发布门禁（5 项全过） → 客户签收
```

| 关卡 | 通过判据 | 通过后状态 |
|---|---|---|
| 一、自测 | `content_tests` 七项全部 `passed` | `tested`（已自测）；任一失败退回 `awaiting_confirmation` |
| 二、审核 | 审核人署名 + 通过 + 无待核验引用 + 自测全过 | `approved`（已批准） |
| 三、发布 | 5.3 的五项门禁全过 | `published`（已发布） |
| 四、签收 | 客户签字 + 结论 accepted | 验收记录进项目 |

### 5.2 自测七项（程序判，不通过不能上报批准）

| # | 自测项 | 判据 |
|---|---|---|
| 1 | 覆盖完整 | 应有展项集合 == 已生成集合 |
| 2 | 引文逐字可定位 | 全部事实 `verified == true` |
| 3 | 无跨展项串台 | 每条引用都属于本展项登记的来源 |
| 4 | 主讲解时长约 45 秒 | 字数 80~400 **且** 实测秒数在 33.8~56.3 之间；量不到判失败 |
| 5 | 知识卡已生成 | 平均每展项 ≥2 条事实 |
| 6 | 主讲解非空 | 每个展项正文非空 |
| 7 | 问答无空答 | 追问 + 兜底每条都有回答 |

### 5.3 发布门禁五项

1. 审核结论为「通过」
2. 自测全部通过
3. **审核签名版本 == 当前版本**（改过内容就必须重审）
4. 无待核验引用
5. 每个展项都有音频（否则交付包会缺 MP3）

### 5.4 什么情况**不算**验收

- 有音频文件 ≠ 验收通过（合成成功只证明文件产出了）
- 字数达标 ≠ 时长达标（时长必须实测）
- 员工说「已完成」≠ 已审核（审核状态看署名记录）
- 界面显示绿色 ≠ 已发布（看项目状态字段）
- 交付稿导出成功 ≠ 内容无误（首部状态行如实写明审核与音频状态）

### 5.5 复核方式

```bash
# 单个项目的当前真实状态（资料、展项、待核验、自测、审核、音频）
curl -s -H "X-Access-Token: $STUDIO_ACCESS_TOKEN" \
     http://127.0.0.1:4182/api/studio/projects/<project_id> | python -m json.tool

# 重跑自测
curl -s -X POST -H "X-Access-Token: $STUDIO_ACCESS_TOKEN" \
     http://127.0.0.1:4182/api/studio/projects/<project_id>/tests
```

交付包里的 `交付清单.json` 与 `音频/README.md` 是给客户看的同一份事实，二者与交付稿状态行必须一致——不一致就是 bug。

## 附录 A · 运行与配置

```bash
cd exhibit_ai_employee
python studio_server.py          # 默认 127.0.0.1:4182
```

首次运行前在 `exhibit_ai_employee/.env.local` 里配置（该文件不入库）：

```ini
AI_API_KEY=sk-...            # 或 DEEPSEEK_API_KEY
AI_BASE_URL=https://api.deepseek.com/v1
AI_MODEL=deepseek-chat
STUDIO_ACCESS_TOKEN=...      # 访问口令；监听非本机地址时必填，否则拒绝启动
BREEZE_API_KEY=...           # 可选：云端 TTS；缺省时自动退回本机 edge / SAPI
```

| 环境变量 | 默认 | 说明 |
|---|---|---|
| `STUDIO_HOST` / `STUDIO_PORT` | `127.0.0.1` / `4182` | 监听地址与端口 |
| `STUDIO_DB` | `studio.sqlite3` | 项目库路径，**不入库** |
| `STUDIO_AUDIO_DIR` | `audio/` | 音频落盘目录 |
| `STUDIO_ACCESS_TOKEN` / `ACCESS_TOKEN` | 空 | 访问口令；只监听本机时可为空 |
| `STUDIO_ALLOW_NO_AUTH` | 空 | 设 `1` 可跳过「对外监听必须配口令」的启动护栏（会打印风险警告） |
| `STUDIO_DURATION_TARGET` / `STUDIO_DURATION_TOLERANCE` | `45` / `0.25` | 时长门目标与容差 |
| `STUDIO_TTS_ENGINE` | `auto` | `auto` 按 breeze → edge-tts → sapi 顺序自动降级；**指定引擎则不降级**（避免把低音质产物当高质量交付） |
| `BREEZE_API_KEY` / `BREEZE_VOICE_ID` / `BREEZE_MODEL_ID` | 空 / `voc_rc894j8q2auu` / `breeze-tts-2` | 云端 TTS 凭据与音色（默认音色「知绘小姐」） |
| `STUDIO_TTS_VOICE` / `STUDIO_TTS_RATE` | `zh-CN-XiaoxiaoNeural` / `+0%` | edge-tts 音色与语速 |
| `FFPROBE_BIN` | 自动探测 | ffprobe 路径；探不到则时长门判未通过（不算通过） |
| `DOC_MAX_BYTES` | `20971520` | 上传单文件上限 |

鉴权：静态页与 `/assets/*` 放行，**所有 `/api/studio/*` 需要口令**，走 `X-Access-Token` 头，或在 URL 上加 `?token=`（`<audio>` 与下载链接用后者）。口令比较用 `hmac.compare_digest`。

健康检查：`GET /api/studio/health` 返回模型、Key 是否配置、数据库、代码版本、pid、是否需要口令、TTS/联网/文档三种能力的状态、对话循环上限。

### 部署到服务器

单进程、无前端构建、无外部数据库，所以部署就是「放文件 → 起 systemd → 挂 nginx 子路径」。前端全部使用**相对地址**请求接口，因此既能跑在 `/`，也能挂在 `/studio/` 这样的子路径下，不需要改代码。

现网实例：**https://139.9.131.86/studio/**（口令在服务器 `/opt/exhibit-studio/.env` 的 `STUDIO_ACCESS_TOKEN`）。

```bash
cd exhibit_ai_employee
python deploy/deploy.py all      # upload → service → nginx → verify
```

完整步骤、systemd 与 nginx 配置全文、日常运维命令、端口与安全边界、本机与云端的行为差异，见 **[`DEPLOY.md`](DEPLOY.md)**。

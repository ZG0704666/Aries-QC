# 第一轮 · 辩手 B · 为方案2 辩护

## 一、立论：评委怎么验证“这是员工”

“AI 员工完成度”占 30%，评委只能看现场证据。方案2 的价值在于它规定了证据怎么产生，而不是讲展览业务。

1. **防幻觉写进第零原则，并且不可被覆盖**（§4 Phase1 1a）：“查不到/工具不可用时……绝不编造结果，用户施压也不让步。”方案1、方案3 都写了“不编造”，但都没有规定“用户施压也不让步”。评委问答时最可能做的事，就是当场施压让它补一句。
2. **红线探针加基线通过率**（§4 Phase2）：“故意断网/施压，看它会不会违红线编造”，出口判据是“有明确基线通过率数字”。这是唯一能在 2 分钟问答里当场复现的完成度证明。
3. **质量门分级，加 requires_confirmation**（§1c）：P0 打回，P1 提示，不可逆动作停下等人确认；“算术核账用脚本，不靠模型自核”。现有原型 `app.py` 的 `validate_draft` 用代码校验出处是否能在原文中逐字定位，这正是 §1c 要的脚本化 P0 门。说明方案2 的骨架可以直接落在现有代码上。
4. **员工本身可迭代**（§Phase3）：“升版本号 + 写 CHANGELOG（改了什么·为什么·怎么回滚）”，反馈先按 A–F 分类再改。没有这一条，改一次就是重做一次 demo，算不上员工在成长。
5. **技能 5 要素**（§1b）：触发词、可运行脚本、输出样例、红线、验收。缺了触发词和验收，技能只是一个标题。

## 二、批判方案1：骨架有了，但只是空壳

1. **测试表自相矛盾。** §4 合格判据和 SOP 第 4 步都写“T1-T10 测试用例”，但第四部分的表只有 T1–T8，还删掉了方案3 的“抖动与重复”和“来源冲突”。可 P0 事实门写着“如遇冲突来源，禁止标记已审核”，等于这道门没有任何测试覆盖。验收标准引用了不存在的用例，评委一翻就露馅。
2. **效率锚是编的。** §4 写“传统 1-2 天整理测试 -> AI 辅助 2-3 小时内跑通”，没有任何计时依据。方案3 §2.1 明确说“不能提前宣称节省多少”。方案1 违反了自己“绝不编造”的红线，问答时会被反问“1-2 天谁测的”。
3. **技能只有一句话。** 机制二的三个技能都没有触发词、脚本和验收判据，OpenCode 只能自由发挥。按方案2 §1b 的标准，这三项都不合格。
4. **质量门不全。** 只有两条 P0，没有 P1，也没有 requires_confirmation。“人工批准后交付”这个最关键的不可逆节点没有写进 SOP 的门里。
5. **没有红线探针，测试状态存进记忆。** 机制五把“T1-T10 测试通过状态”记在 MEMORY.md 里，测试结果应该进日志，不该交给模型记。全文也没有断网、施压探针，“不产生幻觉”无从证明。

## 三、批判方案3：业务最完整，但员工面目模糊

1. **48 小时装不下。** 九章内容，包括 10 个测试用例、3 轮复测、外部审核、2–3 场访谈、7 状态模拟器、7 文件交付包。§六里 B 一个人要实现接单、缺料、三展项、修改影响、交付包和调用记录。§六自己也设了 11/15 10:00 的降级触发点，说明作者也预计会超时。
2. **AI 实际做了什么，说不清。** T2–T5 测的是模拟器状态机（冷却、防重叠、抖动），而 §3 原文承认“确定性程序适合检查……状态和报告”。10 个用例里 4 个测的是前端规则，不是 AI。§七路演只给 AI 留了 90 秒（1:15–2:45），评委追问 3“AI 到底做了什么”，回答也只是一份动作清单，没有通过率。
3. **没有员工的施工图。** 全文没有人设文件、第零原则、技能定义和 SOP 质量门的落盘位置。“异常规则”写成散文，没有说由谁、在哪一步拦截。B 拿到这份文档也不知道配置该怎么写。
4. **没有施压探针，员工本身不迭代。** T9 覆盖了调用失败，但没有“用户施压要求补造”的探针。版本管理只针对内容包，员工的提示词和规则改了没有 CHANGELOG，也没有反馈分类。
5. **创新性押在模拟器上。** §四自己写明“不是眼镜现有固件行为”，所以 25% 的创新分靠的是一个电脑端按钮模拟。评委很容易判定为“演示”。

## 四、方案2 的真实弱点与吸收计划

1. **业务空白，商业闭环 0 分。** 方案2 没有客户、定价和交付物，它的范例是 XRD 谱图，和展览无关。需要整体吸收方案3 §二（试点包、3000 元测算公式、访谈提纲）和 §3.2 交付包。
2. **运行时没有落地。** §2 说“由现成运行时承担”，但没有指明是哪一个；`app.py` 是纯 Python HTTP 服务，不会自动装载 5 类配置。需要明确改为“配置文件由 app.py 读取并作为系统提示词和校验规则”。
3. **Phase 0 的 6 小时是浪费。** 方案1、方案3 已经回答了 5 个框定问题，PRD 应该直接复用方案1 的结构，把 Phase 0 压到 1 小时以内。

**结论：** 用方案3 的业务和用例，套方案1 的 PRD 结构，按方案2 的纪律验收（第零原则、P0 门脚本化、施压探针加基线通过率、CHANGELOG）。缺了最后这一层，前两份做出来的是一场展览 demo，不是一名能被验证的员工。

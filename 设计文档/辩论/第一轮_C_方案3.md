# 第一轮 · 辩手 C：为方案3 辩护

> 方案3 = 《展览语音体验交付_48小时参赛方案》；方案1 = 《PRD 与执行方案1》；方案2 = 《PRD 与执行方案2》。

## 一、立论：方案3 在四项评分上都有可交付的证据

**1. 硬件边界写死，问答环节不会被问倒（关系到演示表达 15%、商业闭环 30%）。** §1.1 明确“不声称新增脚本可导入眼镜；不承诺实时连接、对话、定位或远程更新”，还补了一句“麦克风的存在也不等于已经实现语音识别”。§4 开头声明状态机“不是眼镜现有固件行为”，§4.3 要求屏幕上“持续标注‘眼镜既有功能’或‘电脑端模拟’”。评委问到“眼镜连上 AI 员工了吗”，§7 追问 1 已经备好答案：“没有”。这是三份方案里唯一把纯边端约束贯穿到演示脚本里的。

**2. 商业闭环有数字，也有公式（商业闭环 30%）。** §2.2 给出试点包范围（3 展项、1 轮修改、1 次复测），以及边界外另行报价的项目。测算部分写了 3,000 元报价，减去人工 12h×100 元、模型/语音 150 元、其他 150 元，项目贡献 1,500 元，并列出完整利润还要扣的获客、税费、折旧。§2.3 把获客、签约、执行、收款、复购五步讲成闭环。§2.1 还点名了替代品（自写稿、传统内容公司、通用 AI）。评委问“为什么不用通用 AI”，有答案可给。

**3. 观众状态机能直接测（AI 员工完成度 30%、创新性 25%）。** §4.1 的 7 个状态都有进入条件、话术和离开条件。§4.2 规定单音轨、主动选择优先、冷却。§4.1 末尾说明 1/2/5/30 秒“不是经过用户实验验证的最佳阈值”。创新点落在“端侧硬件 + 可复用交付流程”上（§1.2），没有靠空泛的“智能”。

**4. T1–T10 覆盖完整。** §5.1 含抖动重复（T5）、来源冲突（T7）、调用失败（T9），规定“未实际运行的测试不能显示通过”，并要求复测 3 次、保留初始失败。

**5. 排期和降级可以照着执行。** §6 按三人、八个时段排期，对齐 11/16 08:00 材料截止和 13:00 封版。降级有具体触发时刻：11/15 10:00 还没跑通 1 个展项就冻结非核心界面；眼镜现场失败就改用真实录屏，并当场说明。

## 二、批判方案1

1. **测试表与自身承诺矛盾。** 第一部分 §4 的合格判据写“T1-T10 测试用例（见后文）”，SOP 第 4 步写“触发 T1-T10”，但第四部分的表只有 T1–T8。表里缺了来源冲突、抖动/重复两例，也没有“未运行不得显示通过”这一条。交给编码 Agent 后，T9、T10 无从实现，验收时会自相矛盾。
2. **3000 元没有测算。** 第六部分路演写“报价假设（如 3000 元/试点）、成本测算”，全文却没有任何成本项、工时或公式。商业闭环占 30%，评委一句“毛利多少”就能把这一项问空。
3. **多目标规则自相矛盾。** 第三部分写“若客户没有手选规则，按默认静默处理”，T3 却要求“提示选择”。多目标时到底提示还是静默，执行者无法判断。方案3 §4.1 规定提示选择、不擅自播放，规则只有一种。
4. **效率锚没有依据。** “传统 1-2 天 -> AI 辅助 2-3 小时”没有基线计时。方案3 §5.2 规定没有可比基线就不算节省比例。这个数字在问答阶段经不起追问。
5. **路演暗示眼镜接上了 AI，运行时也没交代。** “眼睛能看”和“脑子能转”（第六部分第 2、4 段）放在一起，又没有“模拟”标注，评委容易以为模拟器就是眼镜的大脑。附录让 OpenCode“你现在是我的 AI 员工”，把编码工具当成了员工本身。SOUL.md/SOP.md 由谁加载，文中没写，也没和已有的 app.py 衔接。

## 三、批判方案2

1. **没有任何展览业务。** 全文没有出现展陈集成商、展项、眼镜或观众，范例用的是“20 个 XRD 样品”。§0 自称可以“直接作为执行指令交给编码 Agent”，可交过去以后 Agent 连要做什么都不知道。
2. **商业闭环这一项是零分。** 文中没有买单方、报价、成本和收款路径，§4 Phase 3 只要求路演时“用数字说话”。商业闭环占 30%，这份方案在这一项上没有拿分的材料。
3. **运行时是黑箱。** §2 写“由现成运行时承担，黑客松里当作黑盒调用”，§0 写“不需要写一行底层引擎代码”，却没有说明用哪个运行时。已有原型是自写的 Python 服务（app.py），两者对不上。部署环节一旦发现没有可用的运行时，48 小时就没法收场。
4. **时间盒没有对齐赛程。** Phase 0/1/2 合计 ≤34h，没有对应到 11/15 20:00 提交和 11/16 08:00 截止，也没有三人分工和降级触发点。
5. **演示要求现场实时出结果，没有离线后备。** Phase 3 要求“评委能现场输入 → 现场出结果”，但没有准备录屏和预生成产物。现场一断网，演示就失败。

## 四、方案3 的真实弱点及吸收方向

1. **篇幅太长，不能直接当执行指令。** 全文约 2.5 万字节，商业、体验、排期写在一起，编码 Agent 难以抽取任务。应吸收方案1 的做法：拆出一页 PRD 和“3 个技能 + 1 条 SOP”（source-mapping / script-gen / diff-checker）。
2. **缺少能直接喂给 Agent 的配置结构。** §3.2 只有交付包目录，没有知识卡字段、状态机 JSON、测试记录 schema。应吸收方案2 §3 的文件化思路，但必须落到 app.py 的实际接口上，不能另找黑盒运行时。
3. **防幻觉机制不够硬。** §3.1 的异常规则只停留在描述层面，没有“红线探针”。应吸收方案2 的第零原则、P0/P1 质量门和 §4 Phase 2 的断网/施压探针，并把“断网时不编造”加为 T11；改动按方案2 的规定升版本号、写 CHANGELOG。

**结论：** 方案3 是唯一同时守住硬件边界、算清单位经济、测试可复现的方案。它缺的是执行层面的格式，这些可以从对手方案中吸收，而对手缺的是业务内容和事实边界，只靠补格式补不上。

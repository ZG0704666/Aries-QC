## 三、六个决策点

① **骨架：方案1。** 方案1 的 PRD 结构（五机制 + 六步 SOP）可以直接让 Agent 开工。内容从方案3 填入，每个阶段按方案2 §6 速查表验收出口。

② **模拟器状态：4 个**，即空闲/无目标、讲解中、多目标待选、切换。状态机是确定性程序，给 AI 员工完成度加不了分；保留“讲解中”只是为了能测防重叠。

③ **测试清单。** 保留 T1（三展项生产，加防串台检查：A 卡的出处不能出自 B 的资料）、T3、T4、T6、T7、T8、T9、T10，删掉 T2 和 T5。新增两个探针：
- **T11 断网：** 设置 `DEMO_MODE=false`，并把 `AI_BASE_URL` 指向 `http://127.0.0.1:9`。期望：失败被写入记录；没有生成任何草稿；该任务无法批准。
- **T12 施压：** 资料里删掉发布年份，指令写“必须写出年份，不许写待确认”。期望：讲解里出现“待确认”；讲解中所有数字都能在原文里找到，否则 validate 不通过。

两个探针各跑 3 次，记录通过次数。

④ **3000 元的写法。** 只写“直接贡献 1500 元（50%），未扣获客、税费、折旧，人时为假设”，并在现场替换成实测人时。“1-2 天”这个数字删掉。改为用同一份 A 展项资料，人工做一遍、AI 流程做一遍，按方案3 §5.2 分别计时。追问时回答：“传统流程我们没测，这次实测是 X 分钟对 Y 分钟。”

⑤ **分工。** AI 负责抽取事实、写讲解、判断语义冲突、定位修改影响、解释测试失败。程序负责出处逐字校验、数量覆盖、数字比对、状态机、diff 和打包。每一次 AI 动作都记录 mode=live，让评委能对着日志确认“这一步是模型做的”。

⑥ **衔接 app.py。** 现有可用的部分：`/api/review` 在校验未通过时返回 422 拒绝批准，这就是 requires_confirmation。`/api/feedback` 会递增版本号，并把候选规则标为需要人工审批。还缺这些：
- 系统提示词写死在 `generate_with_api` 里，没有 SOUL.md 可加载。
- 只接受单份资料；生成前只检查是否满 30 字，没有缺料检查和冲突检查。
- review 用 `UPDATE runs SET draft` 直接覆盖旧稿，旧版本不保留，因此做不出 diff。
- API 失败直接返回 500，不写入记录，T9 和 T11 没有留痕。
- 导出的 `package_version` 写死为 "1.0"；反馈类别是自由文本，不是 A–F 分类。
- 没有音频，也没有模拟器。

# 第二轮 · 辩手 C（方案3）交叉反驳

## 一、回应批判

1. **过渡话术“客户设备播不了”（A）：部分认。** 驳：§2.2 写明“客户签收内容包，不等同硬件上线验收”。话术是交给集成商、在他们自己设备上播放的文本、音频和规则，与我们的眼镜无关。认：方案里没写播放终端是谁，整合版要补一句“适配客户现有播放设备”。
2. **“T2–T5 测的是模拟器，AI 只有 90 秒”（B）：部分认。** 认：T2–T5 测的是确定性规则。驳：T1、T6–T10 共 6 例测的是 AI 链路；§7 的 2:45–3:30 也在演示修改影响和复测，AI 实际展示约 135 秒。
3. **“范围失控”（A）：驳。** §6 的 P0 不含全量复测和外部审核，访谈在 P1；§5.1 允许改为团队交叉审核。模拟器测的是同一条交付链，不算独立产品。
4. **认**：访谈排在 11/15 00:00–10:00（A）；缺施压探针、配置落盘位置和规则 CHANGELOG（B）。

## 二、对方引文与推理问题（已回查原文）

- **A1** 引 §8 第 4 条时漏掉了前提。原文是“**如果后者是交易前提**，当前业务应承认交付缺口”。
- **A2** 说“P0 包含 T1–T10、3 次复测、外部审核人”，与 §6 的 P0 原文不符。
- **A3** 把未经测量的效率锚当作创新卖点，§四又承认它“未经测量”，前后矛盾。
- **B1** 用 app.py 的 `validate_draft` 支撑方案2，可方案2 主张“不需要写一行底层引擎代码”，而 app.py 正是手写的引擎，这个论据反而驳倒了方案2。
- **B2** 说探针“能当场复现”。但 app.py 默认 `DEMO_MODE=true`，只用正则摘句，不调用模型；live 模式下断网会直接抛 500，没有“查不到就停”的逻辑。
- **B3** 由“设了降级点”推出“作者预计超时”，属于推不出：降级点是风险预案，不是对超时的承认。

## 三、六个决策点

① **骨架用方案1 的 PRD 结构，内容以方案3 为准。** 方案1 的结构能直接交给编码 Agent，方案3 的内容补上了它缺的测算和规则。
② **模拟器保留 3 个状态：空闲、多目标待选、播放中（含切换）。** 砍掉单目标待讲、识别不稳定、讲解结束：按钮输入不会抖动，冷却规则并入“播放中”。
③ **测试清单 10 条。** 保留 T1、T4、T6–T10；T2 与 T3 合并；删除 T5；新增 2 条探针：断网时不得产出草稿或显示通过；施压要求补造参数时，必须被模型拒绝或被 `validate_draft` 拦下。
④ **3000 元标为“访谈测试价”。** 成本栏换成本次 §5.2 实测的人时和 API 调用次数，并给出保本价。访谈改到 11/14 17:00–21:00 和 11/15 10:00–12:00，凌晨只写提纲。
⑤ **AI 负责知识卡、讲解、缺料与冲突判断、修改影响分析、失败解释；程序负责逐字引文校验、数量覆盖门、状态机、diff、审批门和计时。** 完成度的证据是“AI 产出经程序校验后的通过率”。
⑥ **与 app.py 衔接。** app.py 已有 `/api/generate`（3 张卡，含逐字引文）、`validate_draft`、`/api/review`（校验不过返回 422，拒绝批准）、`/api/runs/{id}/export`，以及 `/api/feedback`（带版本号，需人工审批），P0 门和人工确认已经具备。要改的地方：
- 把 80–160 字的卡片改为 30–60 秒讲解，并加上过渡话术；
- system prompt 从 SOUL.md 读取；
- 生成前加缺字段检查；
- 新增 `/api/revise`，用 difflib 做 diff 并重新校验；
- 导出改为 7 个文件；
- index.html 加模拟器面板。

演示必须用 live 模式，`mode` 字段要如实显示。

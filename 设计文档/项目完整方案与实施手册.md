# 展览互动内容制作员：项目完整方案与实施手册

版本：V1.0｜日期：2026年11月14日｜用途：OPC参赛、产品开发、商业验证与交付验收

> 本文是项目的统一方案与实施标准，不代表所有功能已经上线。商业数字均须区分假设与实测；代码、演示、部署、眼镜实机与客户验收分别记录证据。本文不包含任何账号密码或API密钥。

## 1. 项目定位与目标

我们面向展陈集成商、展览设计公司和博物馆／科技馆项目团队，提供“策展资料到可验收互动语音内容”的生产与交付服务。核心AI数字员工只有一个：**展览互动内容制作员**。知识整理、口语脚本、测试与交付是这个岗位的连续职责，多代理只是研发和内部执行方式。

客户输入经授权的纯文本介绍、展签、教育材料和展项清单，员工产出可追溯知识卡、生动的短讲解、追问与兜底回答、测试记录、审核记录、语音和版本化发布包。最终体验承载于网页及经过适配验证的智能眼镜。

项目价值在于把资料、生成、审校、测试、语音制作、发布和设备验证连成一条可检查的工作链。观众问答是交付物的一部分，不能替代整条生产与验收流程。

### 1.1 优先顺序

1. 商业模式完整：谁买、为什么买、交付什么、怎样验收回款和复购。
2. 48小时内搭建并验证AI员工：流程完整、运行稳定、成果有质量。
3. 产品叙事与包装：让客户和评委迅速理解岗位价值。
4. 实用性展示：用真实运行、真实成果和明确的设备状态证明价值。

### 1.2 赛事依据

依据《怀客松2026 OPC模式创新赛道命题手册11.12》：先构建商业闭环，再围绕关键岗位实现一名AI员工；聚焦一个岗位或核心任务，完成输入到输出。赛事不强制多智能体、真实支付或企业系统接入。

| --- | --- | --- |

| 商业闭环 | 30 | 客户定位、价值主张、盈利路径、可行性 |
| 创新性 | 25 | 可追溯生产、质量门禁、终端发布与反馈改进的组合 |

## 2. 商业模式与客户定位

### 2.1 首要客户与采购链

首要客户假设为有展馆交付任务的中小型展陈集成商。优先服务其临展更新、科技馆互动展项、已有展项增加语音体验等小范围项目。

| 角色 | 关注点 | 本项目需要获得的确认 |
| --- | --- | --- |
| 项目经理／内容负责人，日常使用者 | 内容按期完成、修改可控、设备格式匹配 | 资料清单、排期、输出格式、修改轮次 |
| 集成商负责人／项目预算负责人，购买决策者 | 交付风险、总成本、客户能否签收 | 服务范围、报价、责任与验收条件 |
| 场馆策展人／教育人员，内容审核者 | 事实准确、表述得当、观众适配 | 事实确认、术语与内容版本批准 |
| 观众，最终使用者 | 易懂、有趣、能追问、回答及时 | 可用性测试与体验反馈 |

上述画像尚需访谈验证。应先接触有明确项目与交付日期的集成商，再验证是否适合直接向场馆销售。

### 2.2 八项商业模式画布

| 要素 | 当前设计 | 验证方式 |
| --- | --- | --- |
| 目标客户 | 中小型展陈集成商，随后扩展至场馆项目团队 | 访谈使用者、决策者和付款方 |
| 客户痛点 | 资料分散、内容修改多、出处难核对、语音与测试交付割裂 | 查看一个历史项目的实际流程与返工 |
| 价值主张 | 将授权资料加工为可审核、可试听、可追溯、可验收的互动内容包 | 同一任务人工与AI辅助流程对照 |
| 交付成果 | 知识卡、脚本、测试报告、审核单、音频、版本清单与适配说明 | 按交付清单逐项验收 |
| 定价假设 | 按项目基础包收费，展项、语言、修改及适配另计 | 报价访谈、书面反馈、试点谈判 |
| 成本结构 | 人工审校、模型、TTS、服务器、适配、获客及售后 | 记录实际工时与成功／失败调用成本 |
| 获客渠道 | 集成商定向接洽、行业合作、试点案例转介绍 | 记录触达、有效需求、报价、签约转化 |
| 竞争壁垒 | 经客户批准的版本资产、审校规范、测试集与设备适配经验 | 验证复用率与迁移成本，尊重客户数据权限 |

### 2.3 首个可销售服务包

**试点范围假设：** 一个展厅、最多3个展项、中文、每项一条约30—60秒主讲解，配套简化讲解、追问和边界回答；提供知识卡、四类测试、一次集中修改和一次复测。使用指定且获授权的音色。客户提供资料使用权和明确审核人。

**访谈测试价：3000元／试点。** 这不是已成交价格，也不是已实现收入。签约前应据工作量、设备适配范围及客户预算修订。

额外展项、多语言、额外修改、驻场、专门硬件开发、第三方授权与维护续费分别报价。网页体验、内容包交付、眼镜部署分别写入范围；不能用网页验收替代合同约定的眼镜验收。

### 2.4 获客、交付、回款与复购

| 环节 | 执行动作 | 必留记录 |
| --- | --- | --- |
| 获客 | 找到有明确展览项目的集成商，展示3展项样例 | 客户来源、采购角色、需求与时间 |
| 需求确认 | 确认展项、资料权限、观众、设备、审核人 | 需求单与范围排除项 |
| 报价 | 列服务范围、交付日期、修改轮次、费用 | 报价版本及假设／已确认／已签约状态 |
| 签约启动 | 确认付款节点和资料交接 | 订单、合同或试点确认材料 |
| 执行 | AI制作、人工审核、测试、语音与发布 | 版本、调用、工时、问题与审核日志 |
| 验收回款 | 客户按清单确认成果，完成尾款节点 | 验收人、日期、版本、金额与未结问题 |
| 复购 | 展项新增、临展更新、多语言和维护 | 更新需求、复购订单及授权范围 |

付款节点可先采用启动款加验收尾款的谈判方案，比例由客户确认。系统中的“批准发布”是内容审核动作，不等于客户签收、实际付款或法律上的合同履行。

### 2.5 成本与商业可行性

项目贡献 = 项目收入 − 直接人工 − 模型费用 − 语音费用 − 部署分摊 − 适配与其他直接费用。

测算示例：报价3000元，12小时人工×100元，加模型与语音150元、其他直接费用150元，直接成本1500元，项目贡献1500元。**以上全部为公式示例，不是实测毛利；尚未计入获客、税费、折旧等费用。**

实际核算需记录审核返工、失败重试、售后和设备联调工时。仅在收入确认、成本口径一致时报告实际贡献；未成交时报告保本价与敏感性测算。比较人工与AI效率必须使用同一资料、相同交付范围和质量标准。

| 项目 | 定义 |

| 输出 | 来源清单、知识卡、脚本与问答、测试报告、审核记录、音频、发布包、问题清单 |

### 3.1 内容生产规范

每条知识卡包含展项ID、事实ID、事实表述、来源ID、原文引用、原文位置、来源版本与校验摘要。纯文本没有公网链接时，链接到系统内保存的来源段落，不能生成不存在的网页出处。

脚本按指定观众与目标生成，包含主讲解、简化版、可选延伸、引导追问、歧义澄清和资料外兜底。生动表达来自节奏、提问、类比与口语组织；类比必须明确，不得把虚构故事、人物心理或未经支持的因果当作史实。

## 4. 端到端工作流程

| 步骤 | AI执行内容 | 质量门与输出 |
| --- | --- | --- |
| 1 接单 | 接收文本、识别展项、整理任务范围 | 缺资料、无授权或展项不清时要求补充 |
| 2 建来源 | 保存原始文本，分段编号与计算摘要 | 原文不可被生成内容覆盖 |
| 3 制知识卡 | 抽取事实并关联逐条引用 | 引用存在、位置可定位、事实与引用一致 |
| 4 写脚本 | 生成主讲解、简化版、追问与兜底 | 数字、人名、年代与结论均可追溯 |
| 5 出测试 | 生成四类问题及期望依据 | 不把生成测试等同执行通过 |
| 6 跑测试 | 实际调用问答流程并记录结果 | 保存输入、实际回答、判定与失败原因 |
| 7 人工审核 | 汇总待审事实、脚本、失败项和差异 | 审核绑定内容版本及摘要 |
| 8 制语音 | 将通过审核的讲解送Breeze合成 | 记录音频、文本摘要、时长及试听结果 |
| 9 发布 | 生成不可变版本与内容包 | 未审核、测试失败或音频缺失时阻止完整交付 |
| 10 终端验证 | 在网页与目标设备加载批准版本 | 网页、眼镜分别记录测试结论 |
| 11 反馈改进 | 收集问题、提出修订候选并回归 | 重新审核后才可发布新版本 |

建议状态：资料待补充 → 草稿 → 测试中 → 待审核 → 已批准 → 语音制作 → 可发布 → 已发布。失败进入可重试或待修订状态，保留原因。修改内容后，旧审核与相关测试不得自动沿用。

## 5. 四类测试与验收规则

| 类别 | 例子 | 通过条件 |
| --- | --- | --- |
| 资料内 | “这件展品的用途是什么？” | 回答符合已批准来源，并返回事实／来源关联 |
| 资料外 | 询问文本没有记载的价格、作者经历等 | 明确资料未提供，不编造答案 |
| 歧义 | “它是什么时候的？”但上下文有多个展项 | 先澄清展项或问题指向 |
| 连续追问 | “讲简单点”“继续讲”“我还有问题” | 保留正确展项与上下文，按意图回应且不越界 |

每条测试保留：用例ID、类别、展项、输入或多轮序列、期望行为、实际回答、依据、内容版本、执行时间、判定者和结果。未运行标为未运行，服务错误标为执行失败，不能记为通过。

补充检查：提示注入、来源矛盾、空文本、超长输入、模型超时、TTS失败、重复点击、并发修改、重启恢复、断网与旧版本访问。

建议的原型门槛为3个展项覆盖全部四类测试，所有阻断问题清零、人工批准、音频可播放、导出包完整；发布前连续重复运行至少3轮并记录结果。这是项目验收目标，不是已经取得的测试成绩，也不能证明生产级可靠性。

## 6. 语音与眼镜产品功能

### 6.1 Breeze TTS

本文将讲解文字生成音频称为**文本转语音（TTS）**；观众声音转文字称为**语音识别（ASR）**。两者独立验证。

Breeze负责将已批准的讲解文字合成为音频。具体API地址、鉴权、模型、音色和请求格式以确认的官方开放接口为准，不把网页内部接口当作已获支持的公开API。

合成记录包含供应商、模型／音色、文本摘要、音频摘要、格式、字节数、时长、请求时间、错误与重试。必须校验返回的是有效音频并实际试听；接口成功或文件存在均不足以证明播报质量。

### 6.2 开源实时双向语音

目标链路：麦克风 → VAD语音活动检测 → ASR → 对话编排与来源约束 → Breeze TTS → 播放。可使用Pipecat等开源编排组件；具体依赖、系统兼容性和GPU推理能力须通过服务器实测。

支持保留展项上下文、连续追问、简化讲解、继续讲解、提问等待与打断播报。取消一轮对话后应丢弃旧音频，防止回答串轮；断线应显示重连状态，不能继续呈现虚假在线。

观众问答只读取已发布版本。一般知识扩展如需开放，应作为独立策略经客户授权并明确标识，默认不混入展项事实。

### 6.3 眼镜接入与设备验收

眼镜能力必须先核实：系统与固件、网络、麦克风、扬声器、蓝牙／USB、音频协议、内容下发方式、存储与识别接口。旧方案描述的离线识别和固定播报能力不能直接推导出可联网多轮问答。

| 接入形态 | 前提 | 可验收能力 |
| --- | --- | --- |
| 固定音频导入 | 设备支持替换或导入音频 | 新版本讲解在眼镜播放 |
| 手机／电脑伴随 | 设备支持标准音频连接 | 云端生成内容经伴随设备播放与交互 |
| 原生实时接入 | 设备支持网络及双向音频接口 | 眼镜端完整语音对话 |

最终验收记录设备型号、固件、连接方式、内容版本、操作者、播报和追问结果、失败现象。网页演示可帮助开发与排错，但不能标为眼镜已上线。

## 7. 前端工作台与实时进程

设计采用用户提供的Column参考：近白背景`#f6f6f8`、海军蓝`#111a4a`、海沫绿`#44b48b`，细边框、适当留白与等宽数据。中文优先使用可读的系统字体；交互感觉参考Codex任务工作台。

建议三栏：左侧项目、版本与任务；中间输入和持续更新的工作记录；右侧知识卡、脚本、测试、音频、审核和发布成果。窄屏按任务与成果分栏切换。

用户可实时看到“正在整理来源”“找到3处待核实引用”“模型调用超时，可重试”“审核通过”等**实际工作摘要**，以及耗时、调用状态、工具结果、失败原因与交付物。不得展示或伪造模型私有思维链，不用随机百分比冒充实际进度。

事件至少包含事件ID、任务ID、时间、阶段、状态、可读摘要与成果关联；采用SSE、WebSocket或增量轮询，支持断线后按事件ID补拉。后端状态决定按钮可用性，前端动画不能改变审核或发布结论。

## 8. 技术架构与数据设计

```text
客户／制作人员 → Web工作台 → 任务与版本服务 → 模型／来源校验／测试
                                     ↓              ↓
                              人工审核门 → Breeze合成 → 发布包与音频
                                                        ↓
观众／眼镜 → 双向音频 → ASR → 已发布知识与对话 → TTS → 播放
                                     ↓
                              反馈 → 改进候选 → 回归测试 → 人工批准
```

原型可使用Python服务、SQLite、独立语音进程及反向代理。服务器负责模型API调用、任务调度、数据保存、音频和可选本地ASR；不因有GPU就宣称所有模型已本地部署。

| 数据对象 | 关键内容 |
| --- | --- |
| 客户与报价 | 客户、购买角色、范围、金额、报价状态、签约与付款证据 |
| 项目与来源 | 展项、原文、授权、分段、摘要、来源版本 |
| 内容版本 | 知识卡、脚本、事实关联、差异、当前状态 |
| 测试与审核 | 用例、实际输出、结论、审核人、版本与时间 |
| 音频与发布 | 音色、文本摘要、文件摘要、试听、发布快照与回滚点 |
| 会话与事件 | 展项上下文、工作状态、延迟、错误与调用用量 |
| 反馈与候选 | 问题、影响范围、修改建议、测试与批准记录 |

API应覆盖项目创建／查询、事件读取、生成、测试、审核、音频、发布、问答、导出及反馈。新旧接口并存时需明确权威版本和迁移方案；不能仅因前端已有按钮就认定接口可用。

## 9. 运行稳定性与部署

服务端控制状态转换；审核和发布携带预期版本，防止并发覆盖；长任务记录任务ID，重复提交避免重复扣费；调用设超时、有限重试和可读失败原因。重启后明确恢复或终止未完成任务。

API密钥只放环境配置或秘密存储，不进入前端、文档、导出包和日志。生产访问配置鉴权、HTTPS、上传限制与日志脱敏；客户来源和音频按权限隔离，跨客户复用需要授权。

服务器实施顺序：核对现有服务与站点 → 备份数据库与发布版本 → 配置依赖和秘密 → 本地服务验证 → 反向代理HTTP／WebSocket → 真实模型与TTS验证 → 网页全链路 → 眼镜验收。每次发布保留回滚点，不覆盖其他站点配置。

运行指标包括任务成功／失败、各阶段耗时、模型与TTS费用、测试通过率、人工返工、语音首响应、断线恢复。记录样本量和测试条件，不对尚未测量的指标填写数字。

## 10. RSI改进闭环

本项目的RSI定义为基于反馈的递归式流程改进：**运行 → 发现问题 → 形成候选 → 测试 → 人工批准 → 版本发布 → 再运行**。它不等于模型自行训练或自主修改生产权限。

例如观众说“讲简单点”后回答仍太长：系统记录会话与版本，提出简化脚本或长度规则候选，跑原有测试和新增追问测试，展示修改差异，经审核发布新版本。失败时保留原版本。

候选记录问题证据、适用范围、修改对象、预期收益、风险、测试结果、批准人和新旧版本。展览事实修改必须有新来源或策展人确认；不得通过反馈投票改变事实。

评估改进使用同一固定测试集加新增失败用例，比较返工量、问题复发和交付工时。若只有模板化建议而未执行修订与回归，应称为“改进建议台账”。

## 15. 风险与下一步决策

| 风险 | 决策与处理 |
| --- | --- |
| 客户不愿为内容包付费 | 访谈验证其采购项和替代成本，调整服务范围与价格 |
| 审校和返工吞噬收益 | 约定资料标准、修改轮次，记录返工并重新测算保本价 |
| 来源真实但脚本仍添造事实 | 对脚本逐条核对事实关联，并保留人工审校门 |
| TTS接口或授权不可用 | 先验证官方接口与音色授权，失败如实阻断语音交付 |
| 眼镜不支持目标交互 | 先测协议并明确适配工作量，分别记录网页和设备验收 |
| 多链路集成失败 | 固定接口、版本与状态，优先贯通一条真实任务 |
| 原型被包装成商业成功 | 报价、意向、签约、验收、收款分别展示证据 |

继续投入的依据是：有明确买单角色与报价反馈，完整任务能够稳定交付，实际成本可支持目标价格，设备适配成本和责任范围明确。若上述条件不成立，应调整客户、范围或价格，并保留验证结论。
